# Руководство по безопасному слиянию и патчингу (Safe Patching & Merge Guide)

> **Назначение документа**: Практическая пошаговая инструкция для инженера на рабочем корпоративном ПК: как зафиксировать свои локальные доработки, накатить исправления от внешних мультиагентов и в случае любых проблем мгновенно откатиться без риска потери данных.

---

## 1. Подготовка: Фиксация локальных доработок перед любыми операциями

Перед тем как вносить любые изменения или подтягивать апдейты из Git, **всегда зафиксируйте текущее состояние**.

### Вариант А: Если на ПК установлен Git (Рекомендуется)

```bash
# 1. Проверьте текущий статус измененных файлов
git status

# 2. Сохраните полный снимок ваших текущих локальных правок в отдельный патч-файл
git diff > my_local_backup_$(date +%Y%m%d_%H%M%S).patch
# (В Windows PowerShell):
git diff | Out-File -Encoding utf8 my_local_backup.patch

# 3. Либо создайте временную изолированную ветку для своих правок:
git checkout -b feature/my-local-enhancements
git add -A
git commit -m "chore: save local work before multi-agent patch"
```

### Вариант Б: Если Git отсутствует или это изолированная папка (Air-Gap)

```bash
# Просто сделайте резервную копию ключевых файлов или всей папки проекта:
# (В PowerShell):
Copy-Item -Path "d:\claw-studio\corporate_speckit" -Destination "d:\claw-studio\speckit_backup_$(Get-Date -Format 'yyyyMMdd_HHmm')" -Recurse
```

## 2. Сценарии накатывания изменений от мультиагентов

### Сценарий 1: Агент прислал diff-патч (`fix_feature.patch`)

Это самый безопасный способ внедрения правок от LLM-агентов.

```bash
# Шаг 1: Сухая проверка (Dry-Run) — применится ли патч без ошибок?
git apply --check fix_feature.patch

# Шаг 2: Если ошибок нет, применяем патч:
git apply fix_feature.patch

# Шаг 3: Если возникли предупреждения о пробелах (whitespace):
git apply --ignore-whitespace fix_feature.patch

# Шаг 4: Проверяем, что изменилось:
git status
git diff
```

### Сценарий 2: Обновление через Git Pull из удаленного репозитория

Если вы забираете обновления из GitHub (`https://github.com/ZnJhbmNpc2Nv/b2bharness`):

```bash
# Шаг 1: Если у вас есть незакоммиченные локальные правки, спрячьте их в stash:
git stash save "local-work-before-pull"

# Шаг 2: Заберите свежие коммиты из основной ветки:
git pull origin master

# Шаг 3: Верните свои локальные правки поверх свежего кода:
git stash pop

# Шаг 4: Если возникли конфликты в файлах (например, в static/index.html):
# Откройте конфликтующий файл, найдите маркеры:
# <<<<<<< Updated upstream
# ... код из репозитория ...
# =======
# ... ваш локальный код ...
# >>>>>>> Stashed changes
# Оставьте нужные строки и сохраните файл.
```

## 3. Чеклист верификации после слияния (Занимает 15 секунд)

После любого слияния или применения патча выполните 3 проверки:

```bash
# Проверка 1: Модульные тесты ядра и REST API
python test_standalone.py
# Ожидаемый результат: Ran 27 tests ... OK

# Проверка 2: Конвейер оркестратора и A2A Swarm
python test_orchestrator_pipeline.py
# Ожидаемый результат: Ran 14 tests ... OK

# Проверка 3: Проверка модулей расширений (Workspace, ReqBank, KnowledgeBase)
python test_modules.py
# Ожидаемый результат: Ran 5 tests ... OK
```

Если все три команды вывели `OK` — система стабильна, регрессий нет.

## 4. Экстренный откат (Rollback): Что делать, если что-то пошло не так

Если после применения правок от агентов тесты упали или интерфейс перестал открываться:

### Если вы использовали Git:
```bash
# 1. Отменить все незакоммиченные изменения и вернуть рабочую директорию в исходный вид:
git restore .
git clean -fd

# 2. Если вы создавали ветку:
git checkout feature/my-local-enhancements

# 3. Если вы сохраняли патч в шаге 1:
git apply my_local_backup.patch
```

### Если вы делали резервную копию папки:
Просто восстановите файлы из `speckit_backup_...`.

## 5. Защита файлов конфигурации и локальных баз данных

Следующие файлы хранят ваши локальные рабочие данные и **не должны перезаписываться**:

1. `specs_storage/speckit.db` — база данных требований, ревизий и аудита.
2. `specs_storage/pipeline_runs.db` — история прогонов конвейера B2B-Harness.
3. `workspace/` — ваша папка с исходниками и PoC-кодом, над которым ведется работа.
4. `dist/` — собранные портативные офлайн-бандлы.

Эти пути защищены: скрипты сервера и тестов никогда не удаляют пользовательские данные без явной команды.
